# Job Schema MVP

Status: Accepted MVP
Created: 2026-08-16
Scope: sourcing output

## Purpose

The MVP `Job` entity stores facts captured from active job postings. It does
not store assessment results, human review decisions, application status, or
historical job-description versions.

Only postings confirmed to be open are saved. Closed, expired, or
indeterminate postings do not create a `Job` record.

## Schema

```yaml
Job:
  job_id: string

  source:
    enum: [Indeed, LinkedIn]
  source_job_id: string|null
  source_url: string

  matched_search_terms: string[]

  role_family:
    enum:
      - CustomerSuccess
      - Growth
      - Marketing
      - ITProjectManagement

  company: string
  title: string

  city: string|null
  country: string|null

  work_mode:
    enum: [Remote, Hybrid, OnSite, Unknown]

  description: text|null
  responsibilities: text|null
  qualifications_requirements: text|null

  description_status:
    enum: [Full, Partial, Missing]

  published_at: datetime|null

  content_hash: string|null

  duplicate_candidates:
    type: list
    default: []
    items:
      job_id: string
      source_url: string
      match_basis:
        enum: [IntraSourceWeakFallback, CrossSourceStrong, CrossSourceWeak]
      confidence:
        enum: [Strong, Weak]
  duplicate_status:
    enum: [Unreviewed, AutoKept, AutoSkipped, ConfirmedDuplicate, ConfirmedDistinct]
    default: Unreviewed

  captured_at: datetime
  updated_at: datetime
```

## Field Definitions

| Field | Meaning / source |
|---|---|
| `job_id` | Internal unique identifier generated by the system. |
| `source` | Job portal from which the posting was captured. |
| `source_job_id` | Job identifier supplied by the source platform, when available. |
| `source_url` | URL of the source job posting. |
| `matched_search_terms` | Actual search term or terms through which the posting was discovered. |
| `role_family` | Role family associated with the sourcing query. IT Project Management is retained in the schema but is inactive under Sourcing Policy v0.1. |
| `company` | Company name displayed on the job page. |
| `title` | Job title displayed on the job page. |
| `city` | City extracted from the displayed job location, when available. |
| `country` | Country extracted from the displayed job location, when available. |
| `work_mode` | `Remote` for fully remote, `Hybrid` for mixed remote/office work, `OnSite` for office/site-based work, or `Unknown` when the page is unclear. |
| `description` | General role, team, company, and position overview. |
| `responsibilities` | Responsibilities, activities, and expected deliverables extracted from the job description. |
| `qualifications_requirements` | Experience, skills, languages, education, and other requirements extracted from the job description. |
| `description_status` | Whether the captured job description is full, partial, or missing. |
| `published_at` | Publication date/time when supplied or reliably parsed; otherwise `null`. |
| `content_hash` | System-generated fingerprint of the job content, used to detect whether a previously captured posting has changed. |
| `duplicate_candidates` | List of every matched candidate relationship; empty when none. Each entry contains the other Job's `job_id`, reviewable `source_url`, match basis (`IntraSourceWeakFallback`, `CrossSourceStrong`, or `CrossSourceWeak`), and confidence (`Strong` or `Weak`). Entries are deduplicated and deterministically sorted by `job_id`; see [`DEDUPLICATION_SPEC_MVP.md`](DEDUPLICATION_SPEC_MVP.md) §4. |
| `duplicate_status` | Resolution state for the candidate pair. `Unreviewed` (default) and `AutoKept`/`AutoSkipped` (Strong-tier auto-resolution) are pipeline-set; `ConfirmedDuplicate`/`ConfirmedDistinct` are set by a human during stage 11 review, including to override a mistaken `AutoSkipped`. See `DEDUPLICATION_SPEC_MVP.md` §3.4/§4. |
| `captured_at` | Time at which the posting was first captured. |
| `updated_at` | Time at which the stored Job record was most recently updated. |

## Example

The following record is illustrative and does not represent a currently live
posting.

```yaml
Job:
  job_id: "job_01J5C7M8Q3K2W9A6B4F1"

  source: "LinkedIn"
  source_job_id: "3998123456"
  source_url: "https://www.linkedin.com/jobs/view/3998123456"

  matched_search_terms:
    - "Customer Success Manager"
    - "Customer Engagement Manager"

  role_family: "CustomerSuccess"

  company: "Celonis"
  title: "Customer Success Manager"

  city: "Munich"
  country: "Germany"

  work_mode: "Hybrid"

  description: |
    The Customer Success team helps enterprise customers achieve measurable
    business outcomes through the company's platform.

  responsibilities: |
    Manage a portfolio of enterprise customers.
    Develop customer success plans.
    Drive product adoption and conduct regular business reviews.
    Collaborate with Sales, Support, and Professional Services.

  qualifications_requirements: |
    Three or more years of customer success experience.
    Experience working with enterprise software customers.
    Fluent English is required.
    German is preferred.

  description_status: "Full"

  published_at: "2026-08-12T00:00:00+02:00"

  content_hash: "4b7c2d989ea540196c8f4fdade367fa8d4911a6bd8cfba9d7bf98657d32d7d41"

  duplicate_candidates: []
  duplicate_status: "Unreviewed"

  captured_at: "2026-08-16T09:35:21+02:00"
  updated_at: "2026-08-16T09:35:21+02:00"
```

## MVP Processing Rules

- Save only postings confirmed to be open.
- Use `source + source_job_id` as the primary deduplication identity when a
  source job ID is available. This is same-source identity dedup
  (`DEDUPLICATION_SPEC_MVP.md` Layer 1) and governs `content_hash`
  update-in-place behavior below; it is unrelated to the cross-source
  `duplicate_*` fields.
- When `source_job_id` is missing, use `source_url` or a combination of
  company, title, and location as a weaker deduplication signal
  (`DEDUPLICATION_SPEC_MVP.md` §2.4).
- When an existing posting has the same `content_hash`, no content update is
  required.
- When its `content_hash` changes, update the current Job record. The MVP does
  not retain historical content versions.
- After extraction, cross-source candidate matching (`DEDUPLICATION_SPEC_MVP.md`
  Layer 2) populates `duplicate_candidates` and `duplicate_status` on both
  matched records. A strictly one-to-one Strong match may set
  `duplicate_status` to `AutoKept`/`AutoSkipped` and exclude the
  `AutoSkipped` record from stages 5–8; a Weak match only sets `Unreviewed`
  and never excludes either record.
- Keep missing or unclear captured facts as `null` or `Unknown`; do not invent
  values.
- Human review and application decisions are outside this sourcing schema,
  except for setting `duplicate_status` to `ConfirmedDuplicate` or
  `ConfirmedDistinct` during stage 11 review.
