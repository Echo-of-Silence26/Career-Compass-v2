## 1. Purpose and Scope

This is the executable extraction prompt for stage 4 (`JobExtractor`): one
call per `RawJobRecord` classified `new` or `changed` by Layer 1 dedup
([`DEDUPLICATION_SPEC_MVP.md`](DEDUPLICATION_SPEC_MVP.md) §2.3), before the
Assessment Eligibility guard
([`DATA_PIPELINE_MVP_SPEC.md`](DATA_PIPELINE_MVP_SPEC.md) §4.3.1).

Per ADR-015, extraction "must only describe posting facts; it must not judge
candidate fit." This prompt never reasons about Hard Disqualifier rules,
Capability Fit, seniority match, or any application decision. It also never
fetches a live page — it works only from the JD text already captured in
this run.

## 2. Field Responsibility Split

The workflow map's row 4 describes the stage as `RawJobRecord -> flat Job
JSON`, but not every `Job` field needs a model call to populate — asking the
LLM to re-derive a fact that is already a clean, source-verified string only
adds hallucination risk for no benefit. This prompt is scoped to the fields
that genuinely require reading and interpreting JD prose; everything else is
assembled deterministically by the `JobExtractor` wrapper around this call.

**Deterministic passthrough — never asked of the model:**

| Field | Source |
|---|---|
| `job_id` | Generated by the system |
| `source`, `source_job_id`, `source_url` | Copied from the `RawJobRecord` |
| `matched_search_terms`, `role_family` | Copied/derived from the `RawJobRecord`'s `query_id` → `query_group_id` → `role_family` lookup in `queries-v0.1.yaml`; never re-derived from JD text |
| `company`, `title` | Copied verbatim from `raw_company` / `raw_title` — both active adapters already return clean strings ([`SOURCE_ADAPTER_SPEC_MVP.md`](SOURCE_ADAPTER_SPEC_MVP.md) §2, §4); re-deriving these from prose risks a mismatch with the source-verified identity |
| `city`, `country` | Parsed deterministically from `raw_location` within the same stage-4 step, not by this LLM call: Indeed's `raw_location` is already a structured object (no split needed); LinkedIn's is one free-text string (`"Munich, Bavaria, Germany"`) split by a small deterministic parser. Both are address-formatting differences, not JD content requiring semantic interpretation — see `SOURCE_ADAPTER_SPEC_MVP.md` §2/§4 ("must happen in the parser, not the connector") and `DEDUPLICATION_SPEC_MVP.md` §3.1 (this split is reused, not re-derived, by Layer 2 matching) |
| `published_at` | Parsed from `raw_publication_date` |
| `content_hash`, `captured_at`, `updated_at` | From the `RawJobRecord` / system clock |
| `duplicate_candidates`, `duplicate_status` | Not set at this stage — populated by Layer 2, which runs after extraction (`DEDUPLICATION_SPEC_MVP.md` §3) |

**LLM-populated — this prompt:**

| Field | Why it needs the model |
|---|---|
| `description` | Requires separating overview prose from responsibilities/requirements prose |
| `responsibilities` | Requires identifying activity/deliverable statements, which are not always under a literal "Responsibilities" heading |
| `qualifications_requirements` | Same identification problem, for experience/skill/education statements |
| `description_status` | A best-effort judgment of whether the captured text looks complete, cut short, or absent — not the deferred semantic-completeness classifier (`DATA_PIPELINE_MVP_SPEC.md` §4.3.1 keeps that post-MVP); this is a lighter, extraction-time signal only |
| `work_mode` | Indeed's `isRemote` boolean (when present) cannot distinguish Hybrid from OnSite on its own (`SOURCE_ADAPTER_SPEC_MVP.md` §2's open question); LinkedIn has no structured signal at all. JD text is the only reliable source for this distinction |

## 3. Required Inputs per Job

The call receives, per job:

- `source` (`Indeed` | `LinkedIn`)
- `raw_title`
- `raw_company`
- `raw_location` — context only; the model must not re-emit city/country
  from it (see §2)
- `raw_publication_date`
- `raw_job_status` — e.g. Indeed's `expired` boolean, when available
- `raw_work_mode` — e.g. Indeed's `isRemote` boolean, when available
- `raw_description` — the full captured JD text; the primary and only
  evidence for every field this prompt produces

No Candidate Profile, Hard Disqualifier policy, or Capability Fit policy is
supplied — this call has no access to them and must not reason as if it did.

## 4. Isolation and Evidence Rules

- Use only the supplied `raw_description` text and the noted structured
  hints (`raw_job_status`, `raw_work_mode`). Do not fetch a live page and do
  not use outside knowledge of the company or role to fill a gap.
- Do not invent, infer, or "clean up" a fact that is not present in the
  text. A missing or unclear fact becomes `null` (text fields) or `Unknown`
  (`work_mode`) — never a guess.
- Do not perform Hard Disqualifier or Capability Fit reasoning. Extraction
  states only what the posting itself says.
- Preserve source wording where practical rather than paraphrasing away
  specific verbs, tools, or numbers (matches
  [`SOURCE_ADAPTER_SPEC_MVP.md`](SOURCE_ADAPTER_SPEC_MVP.md) §1's
  "preservation of source wording").
- Keep `description`, `responsibilities`, and `qualifications_requirements`
  strictly separated by content, not by the source text's own headings — a
  bullet stating a required skill belongs in `qualifications_requirements`
  even if it appears under a "Responsibilities" heading in the posting, and
  vice versa.

## 5. The Prompt

```text
You are extracting structured facts from one captured job posting. Use only
the JD text and source signals supplied below — never outside knowledge,
never a live page fetch, never a guess about what a posting "probably" says.

Given:
- source: {source}
- raw_title: {raw_title}
- raw_company: {raw_company}
- raw_location: {raw_location}        # context only; do not re-emit city/country from this
- raw_publication_date: {raw_publication_date}
- raw_job_status: {raw_job_status}    # e.g. Indeed's `expired` boolean, when available
- raw_work_mode: {raw_work_mode}      # e.g. Indeed's `isRemote` boolean, when available
- raw_description: {raw_description}  # primary evidence — the full captured JD text

Produce exactly these five fields, and no others:

1. description — the general role, team, company, and position overview.
   Exclude specific responsibilities and exclude requirements/qualifications.

2. responsibilities — the responsibilities, activities, and expected
   deliverables stated for this role. Preserve source wording; do not
   summarize away specific verbs, tools, or deliverables. A statement
   belongs here based on what it says, not on which heading it sits under
   in the source text.

3. qualifications_requirements — the experience, skills, languages,
   education, and other stated requirements, including preferred/"nice to
   have" qualifications. A statement belongs here based on what it says,
   not on which heading it sits under in the source text.

4. description_status — one of:
   - "Full" when both responsibilities-type and requirements-type content
     are clearly present in raw_description;
   - "Partial" when raw_description has content but looks cut short,
     preview-only, or is clearly missing one of the two categories above;
   - "Missing" when raw_description is empty or near-empty after
     whitespace trimming.
   This is a lightweight extraction-time signal, not a rigorous
   completeness judgment.

5. work_mode — one of "Remote", "Hybrid", "OnSite", "Unknown". Use
   raw_work_mode as a hint only — it is boolean-only where present and
   cannot by itself distinguish Hybrid from OnSite. The JD text in
   raw_description is the primary evidence (e.g. explicit "hybrid", "N
   days per week in the office", "fully remote", "on-site" language). If
   the text gives no work-location signal at all and raw_work_mode is
   absent or uninformative, return "Unknown" — never guess.

If a field's content is not present in raw_description, return null for a
text field. Do not invent, merge in, or "clean up" facts not stated in the
text. Do not reason about candidate fit, disqualification, or seniority
match — extraction states only what the posting itself says.

Return exactly one JSON object with these five keys and no others, no
markdown fencing, no commentary before or after it:

{
  "description": string | null,
  "responsibilities": string | null,
  "qualifications_requirements": string | null,
  "description_status": "Full" | "Partial" | "Missing",
  "work_mode": "Remote" | "Hybrid" | "OnSite" | "Unknown"
}
```

## 6. Output Contract

```yaml
description: text|null
responsibilities: text|null
qualifications_requirements: text|null
description_status:
  enum: [Full, Partial, Missing]
work_mode:
  enum: [Remote, Hybrid, OnSite, Unknown]
```

These five keys, exactly, map directly onto the corresponding fields in
[`JOB_SCHEMA_MVP.md`](JOB_SCHEMA_MVP.md). No other key
is accepted — an extra key is treated the same as a missing required key
(§7).

### Worked example

Given a `raw_description` equivalent to the Celonis example in
`JOB_SCHEMA_MVP.md`, the expected output is:

```json
{
  "description": "The Customer Success team helps enterprise customers achieve measurable business outcomes through the company's platform.",
  "responsibilities": "Manage a portfolio of enterprise customers.\nDevelop customer success plans.\nDrive product adoption and conduct regular business reviews.\nCollaborate with Sales, Support, and Professional Services.",
  "qualifications_requirements": "Three or more years of customer success experience.\nExperience working with enterprise software customers.\nFluent English is required.\nGerman is preferred.",
  "description_status": "Full",
  "work_mode": "Hybrid"
}
```

`work_mode: "Hybrid"` here comes from JD text stating a mixed remote/office
arrangement, not from `raw_work_mode` alone — illustrating §2's rationale for
keeping this field in the LLM's scope.

## 7. Parseability and Failure Handling

- The response must be exactly one parseable JSON object containing all five
  keys from §6, with no extra keys.
- A response that is not parseable JSON, is missing a required key, contains
  an extra key, or returns an enum value outside the allowed set is recorded
  as an extraction failure, per
  [`DATA_PIPELINE_MVP_SPEC.md`](DATA_PIPELINE_MVP_SPEC.md) §4.3: "A response
  that cannot be parsed is recorded as an extraction failure." Deterministic
  code checks parseability only — it must not silently repair or invent a
  missing field.
- The MVP performs no automatic retry or repair on an extraction failure
  (`DATA_PIPELINE_MVP_SPEC.md` §4.6). The job is marked failed at this stage
  and routed to human review; it does not reach the Assessment Eligibility
  guard.
- On success, the `JobExtractor` wrapper merges this output with the
  deterministic fields from §2 to assemble the full canonical `Job` record
  before it reaches the Assessment Eligibility guard
  (`DATA_PIPELINE_MVP_SPEC.md` §4.3.1), which separately requires
  `description`, `responsibilities`, and `qualifications_requirements` to be
  non-empty strings after whitespace trimming.

## 8. Persistence

Per run, and per job, record the same version/provenance discipline as
[`EVAL_EXECUTION_PROMPT.md`](../llm_eval/EVAL_EXECUTION_PROMPT.md) §1:

- `job_id`, `source`, `source_url`;
- this prompt's version (`job-extraction-v0.1`) and content hash;
- the model / model-configuration identifier used for the call;
- `extracted_at`, `run_id`;
- the raw evidence `content_hash` this extraction was run against, so a
  later content change (`changed` outcome, `DEDUPLICATION_SPEC_MVP.md` §2.3)
  is traceable to which extraction produced the current `Job` record.

## 9. Known Gaps Not Solved By This Spec

- `description_status`'s Full/Partial/Missing judgment is model-assigned and
  unvalidated against a real sample set — it is explicitly a lightweight
  signal (§5 point 4), not the deferred semantic-completeness classifier
  (`DATA_PIPELINE_MVP_SPEC.md` §4.3.1).
- The deterministic `city`/`country` parser referenced in §2 is described
  here by requirement, not yet specified field-by-field (e.g. exact
  comma-split rule for LinkedIn's `"City, Region, Country"` string, or
  behavior when only one or two components are present). It belongs in
  `SOURCE_ADAPTER_SPEC_MVP.md` or a small dedicated normalizer spec, not
  this prompt.
- No fixture-based validation of this prompt has been run yet — it has not
  been exercised against either source's saved sample JDs
  (`data/private/fixtures/`). Treat the worked example in §6 as illustrative
  of the intended shape, not as evidence the prompt performs correctly on
  real postings.
- `raw_job_status`-confirmed-open filtering ("only postings confirmed to be
  open are saved," `JOB_SCHEMA_MVP.md`) is out of scope for this
  prompt; it is a capture-time/deterministic concern, not a JD-content
  extraction judgment.
